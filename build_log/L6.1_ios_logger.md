**Layer:** L6 — The application
**Date:** 25 August 2026
**Status:** ✅ logging path complete end-to-end in the simulator; not yet on device

## Why this is being built now, ahead of its layer

`BUILD_PLAN.md` puts the application last, deliberately: *"Building it earlier
would mean building an interface around numbers whose behaviour was not yet
known."* That reasoning still holds for the **display**, and nothing here
displays a model number.

What changed is D22. Validation is now prospective, which means the exam is
whatever is logged after a freeze — and nothing can be logged well until
something records the right fields. Every session logged in the meantime is
another permanently degraded observation. The logger stopped being the last
thing and became the blocking thing, while the readout stayed last.

The athlete will keep using Spotr in parallel until this is good enough to
replace it, so no data is at risk if the prototype is not yet sticky.

## The measurement that set the schema

`PRODUCT.md` §7.1 through version 0.4 listed the required workout inputs and did
not include equipment context. Building against that list would have rebuilt
the largest error in the cold run.

| | best naive predictor, MAE |
|---|---:|
| free weights (barbell/dumbbell) | **0.0976** |
| gym-fixed (cable/machine) | **0.1657** |

The gap is the labelling, not the athlete. So §7.1 was versioned to 0.5 and two
fields were added as **required at logging time**:

- **equipment context** — which physical station the load was read from. Asked
  only for `cable` and `machine`; free weights are never interrupted for it,
  since demanding it where it does not apply is friction that buys nothing.
- **per-set timestamps** — `DATA.md` §18 has required these since it was
  written and no source has ever supplied one. The synthetic generator applies a
  session at a single instant; the imported archive carries no set clock. The
  Layer 3 audit fails this clause today. Within-session position became a model
  input at L3.14, so a logger that records when each set finished closes a
  standing gap rather than inventing a new demand.

Neither can be reconstructed afterwards. The athlete's historical gym tag is
recollection, and even within one gym `cable_lateral_raise` still spans
3.9 → 16.4 across nineteen sessions.

## What it does

SwiftUI + SwiftData, iOS 17+, defined by `app/project.yml` via XcodeGen so the
project is readable text rather than a binary `.xcodeproj`.

- start a session, tagged with the gym;
- pick from the **1,074-exercise curated library, bundled and pinned at v1.2**;
- record the machine when the movement is cable or machine, with the station
  last used for that movement at that gym offered first;
- log sets — load, reps, RPE, set type — each stamped when confirmed;
- finish, and export JSON.

**Logging is against library `exercise_id` directly.** No name is ever typed.
The whole L3.10 vocabulary-mapping exercise existed because the previous logger
used its own names; this retires that class of problem rather than re-solving
it. Verified: the exported `1_5_rep_leg_extension` resolves in the library, with
equipment `machine` — which is what triggered the context prompt.

## Verified in the simulator, not asserted

Driven end-to-end on iOS 26.5: session creation, gym tagging, library load and
search listing, automatic context prompt on a machine exercise, set entry,
persistence across a relaunch, finish, and export. The resulting file:

```json
{ "schemaVersion": "rhome-logger/1", "libraryVersion": "v1.2",
  "sessions": [ { "gym": "Main gym",
    "entries": [ { "exerciseId": "1_5_rep_leg_extension",
      "equipment": "machine", "equipmentContext": "Cyber by the window",
      "order": 0,
      "sets": [ { "setNumber": 1, "loadKg": 2.5, "reps": 1,
                  "rpe": 9, "setType": "working",
                  "completedAt": "2026-08-25T10:47:50Z" } ] } ] } ] }
```

Every field §7.1 v0.5 requires is present, including both new ones.

## One design defect found by using it

The first set editor used a stepper at 1.25 kg a tap. Reaching 60 kg is 48
taps — unusable in a gym, and it would have produced exactly the lazy logging
the schema exists to prevent. Replaced with typed entry plus 2.5 kg nudges. The
defect was only visible by driving the screen; it would not have shown up in
any test.

## Not done, and stated rather than implied

- **Not on the athlete's device.** The iPhone 14 is paired and a valid signing
  identity exists, but no provisioning profile has been issued and the team is
  not yet set in `project.yml`. Until that happens this is a simulator artefact,
  not a logger.
- **No Python ingest adapter yet.** The export is well-formed but nothing reads
  it. `rhome_eval.spotr` is the model to follow, and its docstring is explicit
  that it is scaffolding for one athlete; this one is the product path.
- **Search could not be exercised by automation** — iOS 26's floating search
  bar would not take focus from the driver. The list, ranking and 1,074-row load
  are confirmed; the search field itself needs a human tap.
- **No model output is displayed.** Deliberate. The readout waits on the
  change-scored criterion and the directional fatigue test.
- **No freeze has been recorded.** D22 requires a freeze commit and date before
  anything logged counts as an exam. That is the next stage, not this one.

## Consequence for the next stage

The clock does not start at this commit. It starts when the app is on the
athlete's phone and a freeze is recorded — and until both have happened, any
session logged is still development data.
