## Purpose

---

## Versioning came first, and the reason is measurable

`generation_config.json` pinned the seed, the commit and every simulator
constant, but not the library. Measured: **nineteen of the twenty-seven v0
exercise ids do not exist in v1** — `bench_press` became
`barbell_bench_press` — so exchanging the file does not subtly perturb the
synthetic dataset, it invalidates it, and nothing in the artefact would have
said which library produced it.

The pin is **content-addressed rather than declared**, the same discipline as
the frozen projections and the scale alignment, for the same reason: a version
string a human maintains is one that eventually lies.

- `data/exercises/LIBRARIES.json` registers each library by SHA-256.
- `ExerciseLibrary` carries its own pin, set at load. Taking the pin from the
  default path would silently mis-attribute any run against a non-default
  library, which is the failure mode that makes a pin worth having.
- `write_dataset` records it and **refuses** to write a dataset whose library
  carries no pin.
- An unrecognised digest reports as `unregistered` rather than raising, so
  authoring a library stays possible while an unpinned one becomes visible the
  moment it reaches a dataset.

Four tests, including the violation: a one-byte edit must change the digest and
report as unregistered rather than inheriting the version it was edited from.

**LIM-18 closed.** The regeneration changed exactly the two predicted files and
every observable and hidden table came back byte-identical.
`tools/layer1_audit.py` goes 52/53 → **53/53**, green for the first time since
L2.1. The artefact is versioned **0.1.1**: the evaluated data is byte-identical
so every Layer 3 result carries over unchanged, but two byte-sequences must not
share one version string.

## Three things the library needed, and only one was a judgement

BUILD_PLAN recorded that validation had found the library "schema-exact". That
claim had been made without ever loading it. It does not load, and fixing that
surfaced a consequence of D16 nobody had anticipated.

### Twelve muscle labels outside the taxonomy — resolved

Two are our own display labels in slug spelling (`upper_chest`, `obliques`) and
need no mapping, only a lookup insensitive to spelling — as D16 predicted. The
other ten fold per D16, including `abductors`, which D16 listed as a spelling
variant but which does not slugify from "Hip Abductors" and needed saying.

The finer label is preserved and recoverable through `library_labels_for`.
D16's commitment was that folding loses resolution in the *model* and not in
what the athlete is shown, and that only holds if the label survives somewhere.

### Fifty-seven `reps_only` exercises with no bodyweight fraction — resolved

`DATA.md` §5.4.1 defines `reps_only` as "body mass via `bodyweight_fraction`",
so an exercise claiming that kind while withholding the fraction claims a load
it has not stated. Classified by `tools/library_kind_review.py`:

| group | n | resolution |
|---|---:|---|
| band work | 32 | fraction stated as **0.00** |
| isometric holds | 14 | reclassified **`time_only`** |
| partial body mass | 11 | proposed fraction, **athlete's review** |

**Bands** move no body mass, so the fraction is zero. Stating it rather than
leaving the field blank is D17 applied: a zero encoded by omission is
unfalsifiable, because nothing can ever disagree with it. Stated, it is a claim
— that a band row contributes dose and no performance observation, which is
right, since the band's tension appears nowhere in the log.

**Isometric holds** are §5.4.1's own worked example: it names "Plank" as
`time_only`, "Recorded, excluded — no repetitions, so no reps-to-failure and no
relative intensity". A dead hang and a Copenhagen plank are the same case.
Reclassifying applies the specification rather than overriding the author, and
it removes them from the dose model, which is the documented v0 boundary.

### The consequence of D16 that only appears once the library loads

`bent_over_barbell_row` names `posterior_delts` as a secondary mover and
`rotator_cuff` as a stabiliser. Both fold to `posterior_delts`, so the exercise
holds one muscle in two tiers — which `Exercise.__post_init__` rejects, and
correctly, because for a hand-authored library that is an authoring error.

It affects **302 of the 1 074 rows**. The largest contributors:

| labels colliding | rows |
|---|---:|
| `posterior_delts` + `rotator_cuff` | 103 |
| `abs` + `obliques` | 59 |
| `abs` + `deep_core` | 51 |
| `traps` + `upper_back` | 47 |

Resolved in the loader, before the `Exercise` is built, rather than by
weakening the invariant. **The highest tier wins**: a muscle named as a mover
is not demoted because a finer label for the same group also appeared below it.

Taking the maximum rather than the sum is the conservative direction and is
stated as a cost, not hidden: the row above contributes the secondary
coefficient (0.50) rather than secondary plus stabiliser (0.50 + 0.20). Adding
them would count one anatomical structure twice because the library happened to
name it twice. Recorded as **LIM-26**.

**Proved inert on v0.** The v0 library resolves **zero** collisions, and the v0
dataset still regenerates byte-identically. A test asserts the zero, because if
it ever becomes non-zero the dataset every Layer 3 number was measured against
has silently changed.

## The result

`exercise_library_v1_1.csv`, registered as **v1.1**:

```
✓ schema valid — 1074 exercises
MUSCLE COVERAGE   loaded at any tier 16/16   primary somewhere 16/16
DERIVATION AGREEMENT   958/1074 = 89% within ±0.15
```

One warning stands: the library's upper:lower region ratio is **1.94**, so
`DATA.md` §3.2's parity target is unachievable from it. That is a fact about the
athlete's library rather than a defect — it is upper-heavy because their
training is — and it does not affect the v0 dataset, which stays pinned to the
v0 library. It will matter if a dataset is ever generated from v1.

## For the athlete

**Eleven exercises need your judgement.** They are repetition work moving part
of your body mass, where the fraction is a lever-arm question the tool should
not answer silently. The proposal is anchored on the two precedents already in
the v0 library — `hanging_leg_raise` at 0.55 and `ab_wheel_rollout` at 0.60:

| exercise | proposed | reasoning |
|---|---:|---|
| `dragon_flag`, `negative_dragon_flag` | 0.85 | near the whole body pivoting at the shoulders |
| `ring_fly`, `suspension_trainer_fly` | 0.55 | lean angle sets the load; mid-range assumed |
| `hanging_windshield_wiper` | 0.55 | matches `hanging_leg_raise` |
| `trx_body_saw` | 0.50 | forearm plank translated |
| `bear_crawl` | 0.50 | locomotion; arguably `distance_time` |
| `suspension_trainer_leg_curl` | 0.45 | hips and legs raised, shoulders grounded |
| `bear_plank_serratus_press` | 0.45 | quadruped press, most mass on the hands |
| `dead_bug`, `bird_dog` | 0.25 | contralateral limbs only, torso grounded |

Run `python3 tools/library_kind_review.py` to see them with their groups.

## Decisions

**The library is not swapped in.** v1.1 is registered, validated and loadable;
nothing yet loads it by default. The v0 dataset stays pinned to the v0 library,
because swapping would invalidate every Layer 3 number and there is no reason to
pay that before Checkpoint 3.

**The athlete's library was amended, not overridden.** Every change is either an
application of `DATA.md` §5.4.1 or a mechanical consequence of no body mass
being moved. The eleven genuine judgements are proposed and flagged, not
applied — the same pattern BUILD_PLAN specifies for L3.10, where the tool
proposes and the athlete reviews.
