## Purpose

Build Rhome's own exercise database — the two-layer structure settled in docs v0.3.

The base layer (name, movement pattern, equipment, muscle tags) is commodity data. The scoring layer (contribution vectors, compoundness, systemic cost, bodyweight fraction) is specific to this model and is what converts a logged movement into a dose. No external exercise database provides it.

This is the stage where the most model behaviour is decided outside of any equation. Whether a Romanian deadlift loads the erectors at 0.5 and costs 0.88 systemically matters more to the output than most coefficients in `MODEL.tex`. It is therefore tested more heavily than its size suggests.

## Validation

**193 tests passing.**

Coverage is complete: all 16 model muscle groups receive load, and every one is a primary muscle somewhere. Both class-band tables from `MODEL.tex` are asserted per exercise. Eight ranking tests encode orderings a coach would recognise — a squat must cost more systemically than a lateral raise, a deadlift must be more compound than a leg curl — because a transposed row in a 16-column CSV is otherwise invisible.

Schema validation rejects out-of-range coefficients, missing primary muscles, duplicate ids, unknown muscle labels, bodyweight kinds without a fraction, and any muscle appearing in two tiers (which would silently double its dose).

The stabiliser asymmetry is pinned directly: grip appears in the deadlift's fatigue vector at 0.20 and is absent from its stimulus vector. ω sums to 1.0 for all 27 exercises and includes stabilisers, since it derives from the fatigue vector rather than the stimulus vector.

Upper/lower parity feasibility is checked here rather than discovered in L1.4: 13 upper, 3 core, 11 lower.

## Findings

### `forearms` was never a primary muscle

Caught by a test asserting that every model group is directly trainable. Forearms appeared only as secondary (curls) or stabiliser (deadlifts, pull-ups, rows).

A muscle group that can only ever be loaded indirectly is not well-formed: it holds a state the athlete has no way to target deliberately. `DATA.md` §7 originally hedged forearms as "optional but useful for pulling", but docs v0.3 promoted it to a full model group without adding an exercise for it.

Added a cable wrist curl to the library and to `DATA.md` §8.1, with a note recording why the pool must contain direct grip work.

### The derivation over-scored barbell isolation

The first form used equipment as the base and adjusted by pattern. A barbell curl derived κ = 0.44, outside the documented isolation band of 0.15–0.30, because the barbell term (0.72) outweighed the isolation penalty (−0.28).

The error was structural rather than a bad constant. A movement's joint count and force demand are properties of the *movement*; the implement modulates them. Restructured so pattern is the base and equipment the adjustment — the same shape systemic cost already used after the v0.3 correction. Barbell isolation now derives 0.28, inside its band, and overall agreement with the curated library rose from 25/26 to 26/27.

Both coefficients now share one form, which is also easier to reason about.

### One outlier remains, and its cause is a downstream consequence of load invariance

The 45-degree back extension is over-estimated on both coefficients (+0.44 κ, +0.43 b). It is tagged `hinge` — the same pattern as a conventional deadlift — and **the model deliberately cannot see absolute load**, so nothing at the point of derivation distinguishes a bodyweight extension from a 200 kg pull.

This is worth recording carefully. Relative-intensity invariance is the right decision for the dose channels and was made deliberately. But it removes the one variable that would separate these two movements when deriving coefficients for a *new* exercise. A design decision that is correct in one part of the system has a specific, bounded cost in another.

The cost is contained: it affects user-created exercises only, and only lightly loaded supported hinges. Adding a `torso_supported` descriptor is the obvious remedy and is **deferred, not rejected** — a single boolean tuned against one exercise would be overfitting a 27-row library. Recorded in `MODEL.tex` as a known limitation, and tracked in `KNOWN_OUTLIERS` with an assertion that fails if it ever starts passing, so the list cannot go stale.

The documented acceptance criterion (≥80% within ±0.15) is met at 96%.

## Decisions

**The CSV is the source of truth; the review page renders it.** `tools/render_exercise_library.py` reads the same file the engine loads, so the page and the data cannot drift apart. A hand-maintained review page would eventually lie.

**The library may be authored in either vocabulary.** The loader accepts display labels or model identifiers, so `Upper Abs|Obliques` resolves to a single `abs` contribution. Tested.

**Known derivation failures are asserted to still fail.** If an outlier starts agreeing, the derivation improved and the entry should be removed — the test forces that to be noticed rather than leaving stale exemptions accumulating.
