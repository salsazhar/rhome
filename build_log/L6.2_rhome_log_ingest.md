# L6.2 — Reading Rhome's own log into the engine

**Date:** 26 August 2026
**Status:** ✅ passed — 12 tests, whole suite 915 passed
**Module:** `src/rhome_eval/rhome_logger.py`
**Tests:** `tests/test_rhome_logger_adapter.py`

## What this is

The counterpart to `spotr.py`: the path from the iOS logger's export to
`DayInput`. Without it L6.1 banks data rather than feeding anything.

It is much smaller than the Spotr adapter, and that is the point. Spotr had to
reconcile a foreign vocabulary, infer set types from a single drop-set marker,
and recover the gym from recollection. This reads a file the app wrote against
the engine's own definitions — `working`/`warmup`/`backoff`/`drop` are already
the engine's `_VALID_SET_TYPES`, and the exercise ids are already library ids.

**Name resolution is gone, not improved.** The logger stores identifiers the
athlete picked from the bundled library, so an id either resolves or the file
is wrong. There is no fuzzy match here and there must never be — matching at
read time is matching with results in view, the failure the frozen L3.10
mapping exists to prevent. An unknown id raises.

## The one design decision worth recording

**Exports are cumulative, not incremental.** The app writes every finished
session on every export, so two exports a fortnight apart overlap almost
entirely. Handled by keying on session UUID with the newest export winning,
which does two things: a correction made on the phone reaches the engine, and
a re-export cannot double-count a month of training.

The test asserts order-independence explicitly — passing the two files in
either order must give the same answer — because "the newest wins" is easy to
write as "the last one read wins", and those differ exactly when it matters.

## Verified

| | |
|---|---|
| Round trip | every field the engine reads survives unchanged |
| Session position | preserved from logged order; the fixture is named so an alphabetical sort would invert it |
| Re-export | supersedes, does not accumulate; order-independent |
| Unknown exercise id | raises |
| Unknown schema version | raises |
| Unknown set type | raises |

| Library version mismatch | noted in the report rather than silently accepted |

## What this did not touch

**The athlete's logged sessions were not read.** Every fixture here is
fabricated. The first real session was logged on 25 August 2026, which makes it
the first genuinely unseen data since the holdout was spent, and building the
adapter against it would have spent it the same way — the failure D22 records,
repeated deliberately. The adapter was verified against known answers instead.

The single real file received to date was checked for *structure only* —
schema, id resolution, muscle routing — and that check is what surfaced the
`PRODUCT.md` §7.1 correction below.

## A correction this stage forced

§7.1 justified equipment context with a within-gym spread on
`cable_lateral_raise` of "3.9 → 16.4 across nineteen sessions". The athlete
challenged it. Checked against `data/real_gym_tags.json`, it was wrong twice
over: the figures are 3.4 → 18.0, and the spread is **between** gyms, not
within one.

| tag | gym | sessions | first-set load | median |
|---|---|---:|---|---:|
| Main gym | DL | 8 | 6.3 → 8.8 | 7.5 |
| Second gym | JD | 21 | 3.4 → 18.0 | 14.0 |

The only set at 15 kg or more anywhere in the log is a single 18.0 on day 349,
at JD. Inside JD the range is mostly a training trajectory — 3.4 rising to a
stable 14.0 by day 340, held for ten sessions — and not a stack disagreeing
with itself.

The field survives, justified by the 1.9× between-room median gap and by the
free-weight/fixed baseline gap (0.0976 vs 0.1657). What does not survive is the
claim that station-level granularity is needed everywhere. §7.1 now says
granularity is the athlete's, per §6.8: where a gym's cables share one
weighting, the gym *is* the context.

**This is a D19 failure and worth naming as one.** A plausible explanation was
available, so the checking stopped. The check took one query, and the wrong
number had already been written into a canonical document.

## Next

The adapter is the plumbing, not the result. Next is the directional fatigue
test (proposal 3) on the **old** 99 sessions, which are already spent
development data: does a muscle the engine calls fatigued actually come in
down? Chance is 50%, so it cannot be rationalised. That verdict decides whether
a readout is worth building at all, and it needs none of the new data.
