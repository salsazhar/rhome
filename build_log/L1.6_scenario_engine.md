## Purpose

Place the thirteen scenarios of `DATA.md` §13 across the two years, and prove each one produces the effect it documents.

The scenarios are what turn the dataset from a long stretch of ordinary training into something that tests specific model behaviour: whether the engine sees a deload as recovery rather than detraining, whether it distinguishes a missed week from illness, whether one unexplained bad session moves its capacity estimate.

## Design

**Scenarios are dials on the ordinary path, never separate branches.** A sleep-restricted day runs through the same sleep model with a different target; a deload runs through the same programme generator with a lower volume multiplier. Branching would risk scenario days differing from ordinary days in ways nobody intended, and would make the scenario itself the thing under test rather than the model's response to it.

`DayModifiers` carries eleven dials whose defaults are the ordinary behaviour, so a day with no scenario active is generated by identical code to one with three.

**Nineteen windows across 730 days**, covering all thirteen families, leaving 67% of days ordinary. Scenarios are episodes against a baseline, not the baseline.

**Both windows are populated.** `DATA.md` §15 requires families to appear in development and holdout with different realisations, and a test asserts that repeated families differ in duration or intensity — the holdout must not be a replay.

---

## Validation

Each scenario is tested against its documented effect rather than against the dial being set. Several are worth naming.

**S2 (failure-heavy)** asserts *disproportion*, not merely elevation: fatigue must rise by a larger factor than the set count does. That is the property `RESEARCH.md` §9.1 draws from Morán-Navarro, and a scenario that merely added volume would pass a weaker test.

**S3 (deload)** asserts the separation that makes deloads work at all: fatigue falls below 75% while adaptation stays above 80%. Either alone would be uninformative.

**S7 (illness)** asserts *concordance* — temperature, resting heart rate, sleep and recovery propensity must all move together — because §13 says the model should recognise multiple agreeing signals rather than react to one.

**S12 (missed block)** asserts the absence of illness markers alongside falling fatigue, since the engine's task is to tell a quiet week from a sick one.

**S11 (bad day)** asserts that recovery context looks *ordinary* on the day of the shock. A bad session the wearables explained would not test anything.

## Findings

### The latent record disagreed with the state it produced

The PR-window scenario applies a recovery bonus. I applied it in the runner, after the recovery model had already computed and recorded the day's propensity — so the hidden ground-truth table carried one value while the physiology was evolved with another.

Caught by the S10 test, which read the latent record and found no improvement. It would not have been caught by watching the simulation behave correctly, because the *behaviour* was right; only the record of it was wrong.

This matters more than an ordinary bug. The hidden tables are what L3 scores the engine against. A latent value that disagrees with the state it generated would have made every evaluation of recovery quality subtly wrong, in a way that looked like engine error rather than data error.

The bonus is now applied inside `RecoveryModel.step`, so the record and the state cannot diverge. The general rule this implies: **any quantity that influences the simulation must be recorded by the component that applies it**, never adjusted downstream of its own record. Recorded as **D13**.

### Two windows had placeholder effect descriptions

A test requiring each window's intended effect to be a substantive sentence caught two that read "Holdout deload." and "As above, in the holdout window." Both are now stated in full, because the manifest is what evaluation reads to know what a window was *supposed* to do.

---

## Decisions

**The manifest is simulator-only**, per `DATA.md` §6.3, and `scenario_manifest` is one of the strings Guardrail 1 scans for in engine source. A test asserts that, so the boundary and the file cannot drift apart.

**Scenario overlap composes rather than replaces.** Multiplicative dials multiply, offsets add, flags take the stronger. The chronology relies on it: the novelty block sits inside ordinary training.

**The runner lives in `rhome_sim/generate.py` rather than in the tests.** L1.8 extends it with file writing, the generation config and the quality report; the loop itself belongs to the simulator.

---

## Deviations from specification

None. Day indices are zero-based, so `DATA.md` §14's "days 71–100" is 70–99 here; §14 states the exact days may be adjusted once the generator exists.
