# L0.2 — Canonical taxonomy, units and time

**Layer:** L0 — Foundation
**Date:** 22 August 2026
**Status:** ✅ Passed
**Tests:** 96 total (71 added this stage)

---

## Purpose

Fix the vocabulary and the arithmetic of time before anything is built on them.

Two things had to be settled here. The first is what a muscle *is* to this system — which, after docs v0.3, means two taxonomies rather than one. The second is how a model that evolves in continuous time reconciles itself with two inputs that arrive as daily aggregates, without producing the calendar-boundary artefacts `PRODUCT.md` §14 forbids.

This stage also builds Guardrail 3, the parameter registry, because L0.3 is about to introduce a large number of specification-derived coefficients and they need somewhere disciplined to live.

## Validation

### Taxonomy

Sixteen model groups, nine upper, one core, six lower. Twenty-four display labels, every one resolving to a valid group, and every group reachable from the display layer — a group nothing could map to would be unreachable from the interface and therefore dead.

The claim boundary is asserted directly in test: `Upper Chest`, `Mid Chest` and `Lower Chest` must collapse to one `chest` state, and likewise for the ab and back regions. If someone later adds a regional model state, that test fails and forces the conversation.

Mass weights are checked for range and for plausible ranking. A transposition in that table would silently distort every derived systemic cost, so quadriceps must outrank chest, glutes must outrank biceps, and quadriceps must be the maximum.

### Time

The headline test is the one `MODEL.tex` explicitly asks for: evaluate state on a fine grid across midnight, on a day with no training and no change in wearable availability, and require smoothness. It samples every minute for 90 minutes either side of midnight and asserts that no step stands out against its neighbours. Because windows are anchored to waking, midnight is an ordinary instant carrying no meaning.

A companion test pins the intended asymmetry: when a recovery window changes, the decay *rate* steps but the state does not. Evidence genuinely arrives once per night, so a rate step is correct; a state step would be an artefact.

The closed-form constant-input solution is checked against 200,000-step explicit numerical integration across every combination of the documented recovery bounds (0.80, 1.00, 1.15) and local half-lives (24, 30, 42 h), agreeing to 1e-5 relative. This matters because the analytic form runs over two years of data, where integration error would accumulate.

Also checked: sustained input settles at its steady state rather than growing without bound; integration is additive across arbitrary split points; the multiplier is neutral before any wearable data exists rather than defaulting to something pathological; and a zero decay coefficient does not divide by zero, even though the model's clip forbids it.

### Guardrail 3

Registered twelve core parameters with evidence grades — six Grade A, six Grade C. Each cites a document and section, and each carries a stable `version_id` for the explanation trace.

**Live demonstration.** The secondary stimulus coefficient was changed from 0.50 to 0.55 in code only. The suite rejected it, naming the parameter, the value and the section that disagrees:

```
AssertionError: stimulus_secondary_coeff = 0.55 is not present in MODEL.tex
§Exercise-to-muscle contribution matrix. Either the code drifted from the
specification, or the specification changed without the registry being updated.
```

Reverted; 96 passing.

## Decisions

**Engine and simulator parameters do not live in `rhome_core`.** The registry *machinery* is core infrastructure, but the values are owned by whoever uses them. `MODEL.tex` coefficients are the engine's priors, and the simulator must not reach for them — that would be an inverse crime routed through a shared module rather than through an import, which Guardrail 1 would not catch.

Core therefore registers only values that genuinely belong to both sides: contribution role defaults, the Nuzzo domain, mass weights, the waking window. Engine priors are registered in L2 and simulator parameters in L1.1, each in their own namespace. Recorded as **D4**.

**A section is taken to include its own heading.** `DATA.md` §7.1 is titled "Model groups (16)", and the count appears nowhere in the body. Excluding headings would have made that parameter unverifiable for no good reason.

**The mass-weight table is the one registry entry exempt from generic verification**, because sixteen values in a two-column LaTeX table cannot be matched as a single literal. It carries a written reason and a dedicated test checking all sixteen individually. A test asserts that any exempt parameter states a reason, so an exemption is always a visible decision.

## Findings

### Guardrail 3 was decorative on first implementation

The first version searched the *whole document* for the registered value. Planting a drift of 0.50 → 0.55 did not fail the suite, because 0.55 appears elsewhere in `MODEL.tex` — as a mass weight and as a bodyweight fraction. The check passed on a coincidence.

This matters more than an ordinary bug. A guardrail that cannot fail provides false assurance, and it would have provided that assurance for the entire remaining project, over the exact class of error it exists to prevent.

Rewritten to extract the cited section — heading, body and any nested subsections, stopping at the next heading of the same or higher level — and search only within it. Two tests now pin the behaviour: a value present in a *different* section must not satisfy the check, and a section that cannot be located is an error rather than an empty scope. An empty scope would have made every check vacuously pass.

The drift is now caught, as demonstrated above.

### A section heading carries information

Caught by the newly scoped checker on its first run: `model_muscle_group_count = 16` failed because "16" appears in the §7.1 heading, not its body. Correct fix was to include headings in section scope.

### Stale bytecode during the demonstration

Two edits to the same file inside one second left Python serving a cached `.pyc`, because its invalidation check has one-second mtime granularity. Not a project defect, but it briefly made a passing revert look like a failure. Demonstrations that edit and re-run within the same second should clear `__pycache__`.
