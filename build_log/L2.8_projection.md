## A projection is the engine, run on a copy

The temptation here is to write the closed form directly — it is four lines and obviously correct. The reason not to is the same one that shaped the ledger at L2.7: a second implementation of decay agrees with the first today and drifts after the next change to either, silently.

So `StateEngine.fork()` produces a copy carrying everything that decides how state moves — the state, the declared activity window, the exposure counts novelty depends on — and the projection advances *that* with the same `advance_to` the real engine uses. A counterfactual set goes through the same `transform_set` and `apply_dose` a real set would. Nothing in `projection.py` knows a half-life.

A test asserts the projection equals the result of simply advancing a fork, to 1e-15. If it ever fails, the projector has acquired arithmetic of its own.

**The ledger is deliberately not carried across.** The explanation trace decomposes states that happened; a projection is a claim about states that have not.

## Three assumptions, made explicit

Every projection carries `assumptions()` in words, because a forecast with its assumptions detached is a number without a claim attached.

**Recovery context resets to neutral.** This is the one that would have been a real defect. The timeline's last window extends indefinitely by design — the engine learns each night as it arrives — so a projector reading it directly would carry last night's ρ across the whole horizon. One poor night would forecast a slow week. `MODEL.tex` names ρ = 1 as the neutral forecast, and a caller who wants to explore a sustained context can pass `assumed_rho` explicitly.

**Background activity contributes nothing, which is the same as assuming a typical day.** Activity amplitude is the *excess* over the athlete's rolling step baseline, so an ordinary future day has amplitude zero by construction. This is worth stating rather than leaving implicit: it looks like the projection ignores daily activity, and it does not — it assumes the usual amount of it.

An activity window still running when the projection is made is carried across, because it is already declared rather than assumed. A test walks the athlete into the middle of a window and requires systemic load to still be accruing inside the forecast.

**A projection never moves the present.** Tested directly, including the counterfactual path. The failure would be invisible: the next real day would simply evolve from a state that had already had an imagined week applied to it.

---

## Decisions

**Counterfactual sets are sorted by time, not taken in the order given.** An interface offering "what if I moved this session to Thursday" will hand them over in whatever order the user edited them, and applying an impulse before one that should precede it produces a subtly wrong answer with no error. A test builds the same two sets in both orders and requires identical results.

**A counterfactual set cannot be placed in the past.** That is not a projection; it is a rewrite of history, and the engine has no mechanism for it — `advance_to` refuses to run backwards for the same reason.

## Notes carried forward

- `MODEL.tex` requires projections to be displayed "with a visibly widening uncertainty representation". The data carries what that needs — a confidence value and band per horizon — but the requirement is on the interface and cannot be discharged here.
- Counterfactual sets currently take a logged effort. An interface will more likely offer "five hard sets" than "five sets at RPE 9", so a later stage needs a mapping from intended effort to RIR. The imputation policy from D18 is the natural place to take it from.
- Projection assumes the athlete's capacity is unchanged over the horizon. Over seven days that is defensible; over the fourteen-day horizon the confidence band already calls limited, it is one more reason the number should not be leaned on.
