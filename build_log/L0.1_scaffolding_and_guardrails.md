## Purpose

Put the project's structural rules in place while the codebase is still empty, when they cost almost nothing to enforce.

Rhome's central methodological commitment is that the inference engine never sees the simulator's internals or its answers. If that boundary is ever crossed, every evaluation result afterwards is worthless — and the failure is silent, because a leaking engine simply appears to perform well. A rule whose violation is invisible cannot be held by convention or memory. It has to be checked by a machine, on every run, from the beginning.

This stage builds that check, plus the reproducibility guarantee and the specification-coverage report.

## Validation

**Result: 25 tests, all passing.**

### Guardrail 1 — import boundary

Rather than only asserting the current tree is clean, the checker is required to prove it catches things. Six tests plant deliberate violations in a temporary package tree and require detection:

- engine importing the simulator (both `import` and `from ... import` forms)
- simulator importing the engine
- `rhome_core` importing upward
- engine referencing `hidden/`, `latent_daily`, `latent_sets` or `scenario_manifest`

Two tests assert the opposite direction — that `rhome_eval` importing both sides is permitted, and that a docstring *describing* the rule is not reported as breaching it.

A final test asserts the checker is actually reading the source tree, guarding against the failure where it passes because it found no files.

### Live demonstration

A real violation was planted in `src/rhome_engine/`, importing `rhome_sim` and referencing the hidden latent file. The suite rejected it with both breaches named and located:

```
rhome_engine/_violation_demo.py:1 [import-boundary] rhome_engine may not import rhome_sim
rhome_engine/_violation_demo.py:2 [hidden-data] rhome_engine may not reference
    simulator ground truth: 'data/synthetic/athlete_a/hidden/latent_daily.csv'
```

The file was removed and the suite returned to 25 passing.

### Guardrail 4 — deterministic seeding

Reproducibility, stream independence, order-independence, seed validation, and a source scan rejecting any use of global random state (`np.random.normal(...)` rather than `rng.normal(...)`). The scanner is itself tested against a planted violation.

The order-independence test deserves note: it asserts that requesting streams in a different order leaves every stream unchanged. This is the property that allows one component to gain an extra random draw later without silently altering every other component's output — the usual way a "deterministic" generator stops being reproducible in practice.

### Guardrail 5 — conformance map

Three clauses registered, three covered, report written to `build_log/conformance.md` by the test run itself. The report regenerates whenever the full suite runs, so it cannot drift from reality. A filtered test run deliberately does not write it, so partial runs cannot overwrite the report with partial coverage.

## Decisions

**Named substreams rather than a single sequential generator.** A single generator means adding one draw anywhere shifts every subsequent number, so an unrelated change silently produces a different dataset. Deriving independent streams by name (BLAKE2b keyed on the root seed) removes that coupling. Python's built-in `hash` was rejected because it is randomised per process and would not reproduce across invocations.

**The hidden-data check scans string literals, not just imports.** The engine will read CSV files by path, so an import check alone would not catch it loading ground truth. Scanning literals for `hidden/`, `latent_daily`, `latent_sets` and `scenario_manifest` closes that route.

**Docstrings exempted from the hidden-data scan.** Discovered on the checker's first run, which flagged `rhome_engine/__init__.py` for a docstring *explaining* that it must not read `hidden/`. Prose about a boundary is not a breach of it. The exemption covers module, class and function docstrings only; every other string literal is still scanned. A test pins this behaviour so the exemption cannot silently widen.

**Guardrails 2 and 3 deferred.** Frozen projections need the engine (L2.4) and the parameter registry needs parameters to register (L0.2–L0.3). Registering them now would create empty scaffolding rather than working checks.
