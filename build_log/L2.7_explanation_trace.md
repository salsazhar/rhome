# L2.7 — Explanation trace

**Layer:** L2 — Inference engine
**Date:** 23 August 2026
**Status:** ✅ Passed
**Tests:** 726 total (28 added this stage)

---

## Purpose

Make every displayed number auditable: decomposed into the exact sets that produced it, with the parameters it rests on and their evidence grades.

Product success criterion 10 requires this. What makes it achievable is that every fatigue state in the model is a sum of exponentially decaying impulses, so exact attribution is available in closed form. The trace is a **decomposition**, not an account written afterwards to sound plausible — and because it is exact, it is checkable rather than reviewable.

## The property that keeps a trace honest

A decomposition can be wrong in a way that never shows: it agrees with the state at first and drifts later, and the drift appears as a confident explanation of a number the engine no longer produces.

The defence is that **the ledger never computes decay for itself.** The state engine accumulates $\Phi(t)=\int\rho(s)\,ds$ as it evolves, and a contributor's surviving value is $d_i\exp[-\ln 2/h\cdot(\Phi(t)-\Phi(t_i))]$ using that same clock. There is no second implementation to disagree with the first.

A test makes the point by running two engines at $\rho=1.0$ and $\rho=0.8$: decay is slower under the lower multiplier, and a ledger with its own notion of elapsed time would agree with the state only while $\rho$ stayed at one.

**Measured over the development window:** 9 347 traces, worst share-sum error **1.3 × 10⁻¹²**, worst relative reconstruction error **1.3 × 10⁻¹²**.

## Two things a decomposition loses quietly

**Background activity is a contributor.** Steps enter as a constant input rate across the waking window, not as an impulse, so a ledger that recorded only sets would find its shares summing to less than one — but only on days the athlete walked, and only by a few per cent. The integrated increment for each segment is recorded at that segment's end, which is exact from that instant onward.

**Spent impulses are folded, not dropped.** After twenty half-lives a contributor retains under one part in a million and is not worth carrying, but discarding it breaks the sum-to-one property that makes the whole trace checkable. Its surviving mass moves into a single residual entry that decays like any other, labelled as what it is — older training whose individual sets no longer matter separately. Over 520 days the ledger settles at about 15 000 entries rather than growing without bound.

## Findings

### Guardrail 3 was verifying values the code never read

Building the parameter block by scanning source for registry lookups turned up five parameters whose registered value was checked against `MODEL.tex`, matched, passed — and was never consulted by the arithmetic:

| Parameter | Shadowed by |
|---|---|
| `stimulus_primary_coeff`, `stimulus_secondary_coeff`, `fatigue_stabiliser_coeff` | dataclass field defaults `1.00`, `0.50`, `0.20` in `Exercise` |
| `waking_window_h` | `WAKING_WINDOW_H = 16.0` in `timeline.py` |
| `nuzzo_domain_min_reps`, `nuzzo_domain_max_reps`, `nuzzo_high_rep_clip`, `nuzzo_near_maximal_anchor` | four module constants in `intensity.py` |
| `steps_baseline_days` | a literal `28` I wrote in the session driver at L2.5 |

The registry said 0.50, `MODEL.tex` said 0.50, the test compared them and passed, and the contribution matrix used its own 0.50 that nothing checked. Editing the literal would have left all three artefacts agreeing with each other and disagreeing with the code.

This is the **third** distinct way this guardrail has been found ineffective — searching whole documents at L0.2, covering one of two registries at L2.6, and now verifying values nothing reads. Each time it reported green.

**The fix is a check in the other direction.** `parameter_reads()` walks the source and collects every registered name the code actually reads, matching on the argument rather than the callable so aliased reads (`p("gamma_hrv")`) and f-string families (`f"phi_stimulus_{rir}"`) are found. Every registered parameter must appear. An unread parameter is either dead or shadowed, and both are defects.

`stimulus_stabiliser_coeff = 0.00` was a fourth case of a different kind: correct behaviour expressed by *leaving stabilisers out* of the stimulus vector. Omission encodes the same result but makes the value unfalsifiable. It is now read and applied, which changes nothing at 0.00 and makes the number load-bearing.

### Naming two contributors when neither dominates

Systemic load spreads across a whole session — its top contributor is typically 8% — and the first driver template dutifully reported "follows Barbell Bench Press set 3 and Barbell Overhead Press set 3". Both statements are true and the implication is false: a state that draws 8% from its largest source does not *follow* it.

When the two leaders together account for under 25%, the driver now names the session rather than the sets. Over the window that is 2 290 of 9 347 strings — a quarter of all drivers were making an attribution the decomposition did not support.

## Claim boundaries, enforced rather than reviewed

`DATA.md` §19.6 requires the last two criteria to be enforced by test. Every generated string passes `check_claim_boundaries()` before it is returned, and the six forbidden examples in `RESEARCH.md` §17 are tested verbatim:

> "Your CNS is 72% fatigued" · "Your chest is exactly 64% recovered biologically" · "An HRV of X means you should not train" · "Your ACWR is 1.4, therefore injury risk is high" · "You are overtrained" · "Your wearable proves you are ill"

All six are rejected, and the six permitted examples pass. The checker refuses percentages in prose entirely — the display index is a number on a screen with help text beside it, but a percentage inside a sentence reads as a measured biological quantity whatever the surrounding words say.

**Over the window:** 9 347 driver strings, 5 948 distinct, every one inside the boundaries.

---

## Decisions

**Traces are built at the close of the day, and only there.** The ledger must be stable while it is read, and the end of a day is the one point at which nothing is mid-computation. Folding happens at the same moment for the same reason.

**The parameter block is read from source, not declared.** A hand-kept list of "parameters this channel uses" is precisely the artefact that stays at its first value while the code moves past it — which is the failure this stage found four instances of.

**Adaptation reports no recovery modifier.** It is not modulated by recovery context, so listing ρ against it would report something that had no effect on the number.

## Notes carried forward

- The parameter block for a fatigue channel currently runs to 29 entries, 24 of them Grade C. That is the disclosure working, but it is also a lot to put in front of a person; the interface will need to summarise it and offer the full list on request.
- Traces are built for every non-zero channel every day, which costs about four seconds over 520 days. Fine for evaluation, worth revisiting if the engine ever runs interactively.
- `Contribution` carries the source reference the specification asks for, but nothing yet resolves it back to a row in the athlete's log. L3.11's ingest adapter should keep source references stable so the interface can link a contributor to the set the athlete actually recorded.
