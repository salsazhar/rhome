# L3.10 — Exercise vocabulary mapping

**Layer:** L3 — Evaluation
**Date:** 24 August 2026
**Status:** ✅ Reviewed by the athlete and frozen
**Tests:** 871 (13 added) · conformance 99/99 · seal intact

---

## Purpose

Resolve the exercise names in the athlete's Spotr log to library ids, and freeze
the result before anything runs.

---

## The disclosure, declared rather than avoided

**This stage opens sealed data.** D9 sealed `data/real/` unread because data
seen during development is data tuned against, regardless of intent. L3.10 is
the one declared exception, and the exception is unavoidable: the engine cannot
run on a log whose exercise vocabulary it has never seen, and discovering that
vocabulary at L3.12 would mean making mapping decisions with the athlete's
results already on screen.

**What was read.** Exactly one query, one column:

```sql
SELECT DISTINCT exercise_name FROM training_sets ORDER BY exercise_name
```

No counts. No dates. No loads, repetitions, effort or set order. No identifiers.
Frequencies are excluded deliberately — knowing which exercises the athlete
trains most would let library curation be steered toward them, which is tuning
through the back door and invisible afterwards. `DISTINCT` discards it inside
the query, so the counts are never in memory.

**The bound is mechanical, not a promise.** `QUERY` is a module constant, and
`tests/test_vocabulary_extraction.py` parses the extractor's own source and
fails if it names any other column of `training_sets` — checking *executable*
strings only, so prose describing the boundary is not reported as breaching it.
A planted violation proves the check rejects a widened query, and a planted
docstring proves it does not reject a comment.

**Result: 68 distinct names**, committed to `data/real_vocabulary.json` with the
query, the disclosure and the archive's digest recorded beside them.

## The seal caught me, which is the seal working

The first version opened the archive with `mode=ro` in a SQLite URI, on the
reasonable assumption that read-only means read-only. It does not. The archive
is in WAL journal mode, and SQLite created `-shm` and `-wal` sidecar files
*inside the sealed directory* on open.

`tools/seal_real_data.py verify` reported **"seal broken: 0 missing, 2 added, 0
changed"** immediately.

Nothing was written to the database — the `-wal` was zero bytes and the
archive's own digest was unchanged — so no harm was done. But two files appeared
in a directory whose entire purpose is that nothing appears in it, and the guard
found them the moment it was asked.

The extractor now **copies the archive to a temporary file and queries the
copy**, so SQLite never opens the sealed file at all. Costs 1.7 MB and removes
the question. A test asserts the copy and forbids `mode=ro` in executable code.

Worth stating plainly: the seal was not decorative here. It caught a real
mistake by the process that was supposed to be most careful about it.

## Matching proposes; it does not decide

BUILD_PLAN's warning was exactly right, and the first version of the matcher
demonstrated it. Accepting any clear winner above a floor put **53 of 68 names
in the confident bucket, and two of them were wrong**:

| logged name | proposed | score | |
|---|---|---:|---|
| Seated Machine Leg Extension | `seated_machine_back_extension` | 0.66 | quadriceps read as spinal erectors |
| Cable Rear Delt Fly | `cable_rear_delt_row` | 0.65 | a fly is not a row |

The first is the instructive one. It sat *between* `Incline Cable Fly` →
`cable_fly` at 0.67 and `Machine Chest Press` →
`single_arm_chest_press_machine` at 0.64, both defensible. **No threshold
separates the wrong 0.66 from the right 0.69**, because the score measures
spelling and the error is anatomical.

So the tool now claims confidence only where tokens agree *exactly* with no
close rival, and refers everything else to the person who knows which machine
they used:

```
68 logged names against 1074 library exercises
  exact  36   tokens agree exactly and no rival is close
  review 31   a candidate exists; the matcher cannot vouch for it
  derive  1   no acceptable candidate, coefficients derived
```

Every `review` row carries its score, its runner-up and two alternatives, so the
review is a choice between named options rather than a re-derivation.

**Nothing is dropped.** `Jackknife` has no library counterpart and is marked
`derive`, not discarded. The L0.3 derivation path gives it coefficients from its
muscle tags and equipment, and L2.6's confidence system already docks dose
quality for a derived coefficient — so it costs accuracy and *says so*, where a
discarded name would silently delete training load from the athlete's history.

## The freeze is enforced, not declared

`rhome_eval.vocabulary` refuses to load a mapping that is not ready:

- **unreviewed** — the proposal writes `reviewed: false` and nothing will run on
  it;
- **incomplete** — a name neither mapped nor deliberately marked `derive` is an
  error, because dropping one would delete training load;
- **unknown name at run time** — raises rather than returning `None`, since
  `None` already means "matched to nothing on purpose" and conflating the two
  would let an unmapped name pass silently into a run that cannot be repeated;
- **content-addressed** — a digest is recorded so a later run can prove which
  mapping it used. Without it, "frozen" means only that somebody intended not to
  change it.

## The review, and what it was worth

The athlete reviewed all 31 through a purpose-built artefact rather than by
editing JSON: each logged name with its candidates as chips carrying
`equipment · primary muscles`, a search over all 1 074, and an explicit
*derive* escape.

**The matcher was overridden on 18 of 68 rows.** That number is kept in the
artefact as `changed_by_review` and asserted by a test, because a review that
changes almost nothing has become a rubber stamp, and the mapping would then be
the matcher's opinion wearing the athlete's authority.

Where the candidates came from:

| | rows |
|---|---:|
| took the top suggestion | 13 |
| picked a different offered chip | 16 |
| had to search for it | 1 |
| chose derive | 1 |

The chips carried the answer 29 times in 31. `Cable Lat Pulldown` →
`mag_grip_lat_pulldown` needed the search, which is the search doing its job.

### The one the tool got wrong

**`Barbell Back Squat` was marked derive, and that was the interface's fault.**
The four chips offered were `paused_back_squat`, `barbell_jump_squat`,
`barbell_split_squat` and `competition_back_squat` — three of them different
exercises. `high_bar_back_squat` and `low_bar_back_squat` were never shown, and
were reachable only by typing into the search box.

Faced with four candidates of which three were wrong, taking the derive escape
was the correct decision *from what was displayed*. It was also expensive: back
squat is the athlete's heaviest systemic lift, and deriving would have replaced
curated coefficients (compoundness 0.95, systemic 0.92, axial 0.95, eccentric
0.75) with values inferred from muscle tags, then docked dose-quality confidence
on every set of it.

Caught by asking rather than by freezing, and corrected to
`high_bar_back_squat` on the athlete's confirmation. The row records why.

**The lesson is about the matcher, not the review.** Its four alternatives are
the four highest-scoring names, and for a query whose plain form exists in the
library the plain form can lose to four decorated variants — `paused_`,
`_jump_`, `_split_`, `competition_` all scored above it. A candidate list that
never contains the obvious answer is worse than a low-confidence one, because
the reviewer cannot tell the difference between "the library lacks this" and
"the matcher did not offer it". Recorded as **LIM-28**.

## For the athlete

Nothing outstanding from this stage. `Jackknife` is the single derived name —
the library genuinely has no counterpart, so its coefficients come from muscle
tags and its dose quality is docked accordingly.

## Decisions

**The extraction is a superset on purpose.** No filter for deleted sets or
workouts. A vocabulary covering a name the athlete no longer uses costs nothing;
one missing a name the adapter later meets fails at L3.12, which is the run that
cannot be repeated.

**The mapping targets library v1.1**, not v1 — the version L3.9 registered after
resolving the muscle labels and the `reps_only` fractions.
