# L3.11 — Real-data ingest adapter

**Layer:** L3 — Evaluation
**Date:** 24 August 2026
**Status:** ✅ Built, round-tripped, both source gaps resolved by the athlete
**Tests:** 885 (14 added) · conformance 100/100 · seal intact

---

## Purpose

Read the Spotr SQLite archive and the Oura trends export into the engine's own
schema, without opening the seal.

**Scope: this athlete, not the product.** The Spotr archive exists only because
it was scraped from a device export; no user will arrive with one. This is
validation scaffolding for L3.12. General import belongs in Layer 6, and is not
a mitigation the engine may assume it has.

---

## A second disclosure, and why it was necessary

L3.10 took the exercise names. This stage needed the *encodings*, for the same
reason: an adapter cannot map `set_wdf` to a set type without knowing what
values `set_wdf` takes, and a warm-up read as a working set corrupts every dose
downstream — silently, in a run that happens once.

Bounded the same way, and recorded in `data/real_conventions.json`: the distinct
values of **four categorical columns**, no counts, no dates, no per-set data.
`PERMITTED` is a module constant of `(table, column)` pairs and every query is
built from it alone.

| column | values |
|---|---|
| `training_sets.set_wdf` | `Dropset` — and nothing else |
| `training_sets.exercise_type` | `weight_reps`, `reps_only`, `time_only` |
| `health_data.data_type` | `active_calories`, `hrv`, `readiness_score`, `resting_hr`, `sleep_hours` |
| `user.default_weight_unit` | `kg` |

Knowing that `set_wdf` takes one value says nothing about how the athlete
trains, in the way that knowing a column exists says nothing. Two of these four
answers turned out to be findings in themselves.

## What the sources do not have

### The logger cannot mark a warm-up

`set_wdf` has exactly one value. There is no warm-up marker and no back-off
marker. In the real log a warm-up — if the athlete logs them — is
indistinguishable from a working set and arrives carrying **full dose**.

For scale: the synthetic dataset is 25% warm-ups, all correctly contributing
nothing. If the real log is comparable and they read as working sets, every
fatigue state at L3.12 is inflated, evenly, and therefore invisibly.

**Resolved by the athlete: they have never logged one.** Spotr can record
warm-ups; they simply never have, so there are no rows to misread and the
concern does not arise. LIM-29 closed.

What it does mean is narrower and worth keeping: the athlete's log is
**entirely working sets**, so the set-type machinery built at L2.1 goes almost
wholly unexercised on real data, and only `Dropset` will test it.

### There is no body-mass series

`health_data` records HRV, resting heart rate, sleep, readiness and calories —
not weight. The only body mass anywhere is `user.weight_in_pounds`, a single
current figure. Oura carries none either.

`Pull-Up`, `Chest Dip (Weighted)` and `Decline Push-Up` are all in the athlete's
vocabulary, and `effective_load` returns `None` without a body mass, so those
sets will contribute dose and no performance observation. Supplying the single
current figure would be *worse* than supplying nothing: every historical pull-up
would read at today's weight and the engine would call the difference strength.

**Resolved with four recalled anchors**, supplied by the athlete and committed
to `data/real_body_mass.json` — 61.0 kg in August 2025, 63.0 at the turn of the
year, 66.0 in late April 2026, 65.5 now. They are labelled as *recollection*
everywhere they appear, because a number that looks measured and is not is worse
than an absent one.

Two decisions keep that honest. **Linear between anchors and nothing outside**:
extrapolating would invent a trend where there is not even a recollection, so
the **241 days of Oura record preceding the first anchor** carry no body mass at
all. **No synthetic fluctuation**: the athlete asked for realistic variation, but
adding noise would make recalled figures look measured, and `BodyMassTracker`'s
seven-day median would then dutifully remove wobble that never existed. A test
asserts the daily delta is constant between anchors, so noise cannot creep in
later.

The residual cost is stated rather than absorbed: a 1 kg error on 65 kg is ~1.5%
of load on a pull-up, carried into capacity. Every bodyweight-exercise capacity
figure at L3.12 carries a few per cent of uncertainty that is not the model's,
and the scorecard must say so. LIM-30 mitigated.

## What the adapter does

`rhome_eval.spotr` joins two sources into `DayInput`:

- **A continuous calendar**, not one entry per session. The engine evolves state
  in real time, so a fortnight away from the gym arrives as fourteen empty days
  rather than a gap between two entries — that absence is the information
  (`DATA.md` §19.5).
- **It resolves no exercise name itself.** Every name goes through the mapping
  frozen at L3.10, and an unseen name raises. Matching at read time is matching
  with the athlete's results in view.
- **Oura's readiness score never reaches the engine.** `DATA.md` §5.1 forbids it
  as a predictor because it is generated from overlapping underlying variables.
  It is not carried into `RecoveryReading` at all — structural rather than
  remembered — and a test asserts the value cannot be found in any channel.
- **Units are converted, not copied.** Oura reports sleep in seconds and
  efficiency as a percentage; the engine wants minutes and a fraction.
- **Nothing is invented.** No body mass, no anchor efforts, no set types the
  source does not carry. Tests assert each absence.
- **The archive is copied before it is opened** (LIM-27).

## The round trip, which is the whole design

The adapter is tested by writing the **synthetic dataset into Spotr's shape** —
a SQLite database with the archive's full 37-column width, plus an Oura-shaped
CSV — reading it back, and comparing against what the engine gets from the
synthetic CSVs directly. The seal stays shut while the parsing is debugged,
which is where the work is, and the comparison has a known answer.

Over 120 days and **1 771 sets**: every set survives, and loads, repetitions and
effort match exactly. What does not survive is asserted rather than tolerated —
the 400-odd warm-ups come back labelled `working`, which is LIM-29 measured
rather than described.

### The bug the fixture caught

The fixture stores every column as `TEXT`. The first adapter read **all 1 771
rows as deleted**.

SQLite is dynamically typed: a column declared `INT` can hold the string `"0"`,
and `if row["workout_is_deleted"]` on `"0"` is `True`. The real archive happens
to store integers — so a fixture that copied the declared types would have
passed, and the adapter would have been correct by luck about a detail of one
export.

`_as_flag` now interprets every storage class SQLite allows. The fixture keeps
`TEXT` deliberately.

## Decisions

**The disclosure was taken rather than worked around.** The alternative was an
adapter that discovers encodings at run time and refuses on anything unfamiliar
— safer in principle, but it moves the failure into L3.12, which is the one run
that cannot be repeated. A bounded look now is cheaper than a wasted opening.

**Body mass is a dated series, not a constant.** A single figure from
`user.weight_in_pounds` would have scored every historical pull-up at today's
weight and let the engine call the difference strength. The series is keyed by
date, absent outside the recollection, and never imputed.

## Notes carried forward

- **L3.12 must report bodyweight-exercise capacity separately** from barbell
  lifts, because those figures rest on recalled body mass and the others do not.
- Sessions before 15 August 2025 yield no performance observation for `Pull-Up`,
  `Chest Dip (Weighted)` or `Decline Push-Up`. How many is unknown until the run.
- A weight-tracking feature is planned for the product; it turns this
  reconstruction into a warm start and should be built before the next cold run.
- `TYPE_TO_KIND` maps `exercise_type` but nothing consumes it yet: the frozen
  mapping already resolves to library exercises that carry their own kind. It is
  kept because a `time_only` row reaching the dose model would be a defect, and
  L3.12 should assert it does not happen.
