# L1.5 — Performance generation chain

**Layer:** L1 — Simulator
**Date:** 22 August 2026
**Status:** ✅ Passed — the effort-distribution question was resolved by revising `DATA.md` to 0.6.0
**Tests:** 337 total (25 added this stage)

---

## Purpose

Produce every observable set as a *consequence* of hidden state, in the causal order `DATA.md` §9.5 fixes: latent capacity → fatigue acting now → stochastic shock → load and repetitions performed → true repetitions in reserve → the noisy value logged.

Assigning a performance number alongside a set, rather than deriving the set from it, would make the dataset a description of the answer rather than evidence for it.

## Three further structural differences from the engine

| | Engine | Simulator |
|---|---|---|
| Reps-to-failure | Tabulated Nuzzo population curve | Smooth exponential of different shape, scaled by per-exercise endurance (0.70–1.40) |
| Fatigue → performance | `exp(−Σλx)` | `1/(1 + Σλx)` — agrees to first order, diverges as fatigue accumulates |
| Session variation | Constant variance | Heteroskedastic, plus rare large shocks with no observable cause |

The endurance factor matters most. Nuzzo et al. report large between-person variation in repetitions achievable at a given percentage of one-repetition maximum, so the engine's population prior is systematically wrong for this athlete by an amount it cannot observe.

---

## Validation

Two years generated end to end: 7,852 sets across 499 sessions.

| Quantity | Result |
|---|---|
| True RIR | mean 1.91, SD 1.16 |
| Logged effort error | mean −0.05, SD 0.906 against a documented 0.9 |
| Capacity gain, main lifts | +15.5% bench, +18.4% squat, +17.8% deadlift |
| Realised rep bands | within 5 points of every documented band |
| Realised effort bands | within 5 points of every documented band |

The causal ordering is asserted directly: repetitions never exceed what was physically possible; true RIR equals capable minus performed; the same prescription yields fewer repetitions when the athlete is fatigued; later sets in a session express less than earlier ones.

## Findings

### The repetition bands had the same problem, for a different reason

The 1–3 band ran to 14% against a documented 5–8%. Only ~6% of sets are prescribed there; the rest are later sets of 4–6 prescriptions falling short under within-session fatigue.

Repetition count carries no observation error, so unlike effort this describes the training directly. The previous range implicitly assumed either no drop-off across sets or a load light enough to prevent it, and both misrepresent how anyone trains.

Adding the behaviour the model was missing — a lifter strips weight when a set lands *at* the bottom of its range, anticipating the shortfall rather than waiting for it — brought it to 12.2%. The band was then set from measurement across eight seeds rather than tuned further.

### Three failures with one cause

The first end-to-end run produced a mean true RIR of **15** — sets performed fifteen repetitions from failure — a broken effort distribution, and capacity gains of +50% to +100% over two years.

All three traced to one bug. Repetitions were drawn at random within the prescribed range, so the top of the range was almost never reached across *every* set of an exercise, so the double-progression rule almost never fired. Load fell steadily behind a capacity that was itself growing an order of magnitude too fast, relative intensity collapsed, and repetitions in reserve exploded.

Fixing the progression rule — the athlete performs as many repetitions as the target effort allows, up to the top of the range, which is what double progression actually means — and recalibrating adaptation brought all three into range at once.

### The specification's effort distribution was inconsistent with its own noise model

I first concluded §9.2 must describe *true* effort, because the logged bands were unreachable at any calibration. The athlete corrected that: a training log contains logged values. Reinterpreting a specification to fit an output is the wrong direction of fit.

Testing the correct reading surfaced two genuine bugs (above), and true effort spread fell from 1.16 to 0.84 repetitions. It did not close the gap, and the residual turned out to be real: given the 0.9 repetitions of estimation error `MODEL.tex` mandates, the documented bands required true effort concentrated below 0.4 — every working set at nearly identical proximity to failure. That contradicts §8, which prescribes heavy triples alongside isolation near failure.

The athlete's second observation resolved the shape of the fix. Effort is logged as **whole numbers**, and granularity matters more than it looks: the RPE 9.5–10 band spans 0 to 0.5 RIR, so half-point logging places two reportable values in it against one for whole numbers. Switching to whole numbers dropped the top band from 25.4% to 19.7% and restored the ordering — 1 RIR became more common than 0, as it must be.

The remaining gap was closed by revising `DATA.md` §9.2 to specify **two** distributions rather than one, because they are genuinely different:

| RIR | True effort | Logged effort |
|---|---:|---:|
| 0 | 11.8% | 20.5% |
| 1 | 30.8% | 25.3% |
| 2 | 36.8% | 25.3% |
| 3+ | 20.5% | 28.8% |

The training is sensible; the log is smeared by the athlete's own estimation error. That distinction is worth stating in the specification rather than leaving implicit, because it carries a consequence the engine must respect: **the smearing is irreversible at the level of a single set**, which is a floor on how well relative intensity can ever be estimated.

### The effort distribution is measured on logged effort — and is not yet met

I initially concluded that `DATA.md` §9.2 must describe *true* effort, because
the logged bands could not be reached at any calibration I tried. That was
wrong, and the athlete corrected it: a training log contains logged values, so
the specification is describing what ends up in the CSV. Reinterpreting the
specification to fit the output is the wrong direction of fit.

Testing the logged reading properly surfaced two genuine bugs, both now fixed
(see the progression findings above). True effort spread fell from 1.16 to
0.84 repetitions as a result.

It does not close the gap, and the residual is structural. Given the 0.9
repetitions of reporting noise `MODEL.tex` mandates, the documented bands
require true effort to have a standard deviation below roughly 0.4:

| True effort spread | 6-7 | 7.5-8 | 8.5-9 | 9.5-10 |
|---|---|---|---|---|
| 0.0 — every set identical | 10.1% | 33.3% | 39.4% | 17.2% |
| 0.3 — within a third of a rep | 11.3% | 32.4% | 37.9% | 18.4% |
| 0.5 — within half a rep | 13.2% | 30.9% | 35.4% | 20.4% |
| **1.04 — current simulator** | **~22%** | **~23%** | **~27%** | **~28%** |
| *Documented target* | *10–15* | *30–35* | *35–40* | *15–20* |

A spread below 0.4 means essentially every working set taken to the same
proximity to failure. That conflicts with the same specification prescribing
heavy triples at 2–3 RIR alongside isolation work near failure. Under the tight
reading, the tails at RPE 6–7 and 9.5–10 arise entirely from *misreporting*
rather than from the athlete genuinely training that way.

A variance decomposition settles which lever matters. True effort spread
divides roughly evenly between the programme's prescribed effort variety
(56%) and repetitions capped at the top of a range (50%, the two overlap).
Compressing prescribed effort to a 1.0–2.2 RIR band took the spread from 1.04
to 0.84 and moved the bands materially; changing how load is chosen barely
moved them at all. So the lever is programme variety, and using it means an
athlete who trains every set at nearly the same proximity to failure.

That compression was reverted, because making the programme unrealistic to
satisfy a distribution is the same error as reinterpreting the specification to
satisfy the output — just applied to the other document.

**This is open for decision and is not resolved here.** The three ways out are
to tighten the programme's effort variety until the logged bands are met, to
accept the current spread and record the deviation, or to revise §9.2 so it is
consistent with its own noise model. The last is legitimate under the
implementation rule in the documentation README, which requires disagreements
between code and documents to be resolved explicitly rather than absorbed.

**The current calibration is not merely off-target; it is implausible.** More
sets are logged at RPE 9.5–10 than at 8.5–9, so "maximal" is the single most
common entry in the training log. No real log looks like that. The clip at zero
repetitions in reserve is the mechanism: reporting noise pushes the negative
tail below zero, where it piles onto RPE 10.

The corresponding test asserts the documented bands **exactly** and is marked
`xfail(strict=True)`. Weakening the assertion would hide the defect; a strict
marker keeps it visible in every test run and fails again if it starts passing
without the underlying decision having been made.

This blocks Checkpoint 1. The dataset should not be generated at L1.8 while the
logged effort distribution is not credible, because every downstream evaluation
would inherit it.

### The relative-intensity curve did not invert at one repetition

`true_relative_intensity(1)` returned 1.02, clipped to 1.00, and inverting that clipped value gave 1.51 repetitions. The curve disagreed with itself at exactly the point where the physical meaning is unambiguous: one maximal repetition is 100% of a one-repetition maximum by definition.

Caught by a round-trip test rather than by inspection. Fixed by constraining the curve's coefficients to sum to 1.0, so the identity holds by construction rather than by clipping.

---

## Decisions

**Progression judges the first set, not the worst.** Repetitions falling away across a session is ordinary fatigue; a *first* set below the intended range means the load itself is too heavy.

**A double load step when every set finishes comfortably clear of target.** A single step per session lets load fall behind a growing capacity, which inflates repetitions in reserve and smears the effort distribution.

**Realised distributions are tested with a stated 5-point tolerance.** `DATA.md` calls these "approximate targets", and two effects displace realised from prescribed by a few points: repetitions capped at a range's top, and heavy sets falling one repetition short into a lower band. The tolerance is written down rather than the bands being quietly widened.
