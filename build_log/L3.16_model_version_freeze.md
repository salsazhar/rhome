# L3.16 — Freezing a model version, so the prospective exam can exist

**Date:** 26 August 2026
**Status:** ✅ passed — 9 tests, whole suite 924 passed
**Modules:** `src/rhome_eval/version.py`, `tools/freeze_version.py`
**Tests:** `tests/test_model_version.py`
**Clause:** `ARCH:model-version-freeze-stamp`

## What this is, and why it had to come first

D22 moved validation to a prospective footing: the recurring exam is every
session logged *after* a model version was frozen, because those cannot have
been fitted to. `BUILD_PLAN.md` states the requirement plainly —

> Every model version must be stamped with the date it was frozen, and every
> evaluation must state which sessions post-date that stamp. Without that the
> regime is a claim rather than a procedure.

It was a claim. Searching the repository for a freeze date found prose in
`DECISIONS.md` and `RESEARCH.md` and no mechanism anywhere. The athlete has
been logging through Rhome since 25 August; without this, nothing could say
which model those sessions post-date, and the strongest validation resource
the project has was accruing against no reference at all.

It comes first in the fixing phase for a second reason: **the reference version
must be frozen before any repair touches the engine.** Freeze after fixing and
there is nothing to compare the fix against.

## The freeze date is derived, never declared

The temptation this design exists to remove is backdating — freezing today and
claiming a date that makes more sessions count. So `frozen_at` is not supplied.
It is read from the last commit touching anything that decides what the engine
predicts, and the version's digest is computed from the code and parameters
actually present.

That is the same argument the library pin and the frozen projections already
make in this codebase: *a version string a human maintains is a version string
that eventually lies.*

Two groups, kept apart because they answer different questions:

| Group | Contents | Effect |
|---|---|---|
| `engine` | `src/rhome_engine/`, `src/rhome_core/`, the exercise library | decides what the engine predicts; a change here **is** a new version and moves the freeze date |
| `inputs` | real-data mapping, conventions, gym tags, body mass | decides what the engine *sees* on the historical log; recorded as evidence, does not make a new model |

The prospective logger writes library ids directly, so the name mapping does
not apply to prospective data at all — which is why it sits in the second group.

## What the date turned out to be

Established rather than assumed, as the plan required:

```
src/rhome_engine/     last changed  2026-08-24 22:23  39f385d
src/rhome_core/       last changed  2026-08-24 22:23  39f385d
exercise library      last changed  2026-08-24 22:23  39f385d
```

Everything committed since is L6.1 (the iOS logger), L6.2 (its ingest adapter)
and L3.15 (diagnostic tools). None touches the engine — confirmed by
`git show --stat` on each.

**So v0's honest freeze date is 2026-08-24T22:23:33+01:00, and every session
the athlete has logged since 25 August genuinely post-dates it.** Freezing
today forfeits nothing. That was worth checking rather than assuming: the
conservative reflex would have stamped today's date and silently discarded the
first sessions of the only prospective record that exists.

## v0 carries a known defect, and says so

`known_defects` is part of the record, and v0 is stamped with **LIM-38** — the
novelty inflation that fires for movements the athlete already knew, touching
42.4% of the historical log. A version frozen with a known deterministic fault
is still worth freezing, because it is the reference the repair must beat. What
it must not do is let a later reader mistake its score for a clean one, so the
defect travels with the record and `freeze_version.py` prints it under a line
saying exactly that.

## Guardrails: what was attempted

Tests attempt the violation rather than asserting about the mechanism.

| Attempt | Outcome |
|---|---|
| move a registered parameter, keep the stamp | refused — digest moves |
| edit engine source, keep the stamp | refused — digest moves |
| edit a recorded version after the fact | `verify()` fails |
| freeze the same model twice under two labels | refused, by digest and by label |
| read a freeze date from a tree with uncommitted engine changes | refused |
| carve a file out of the digest that the engine can import | guarded by import scan |

That last one is the interesting one, and it was found by the guardrail firing
during development rather than by design. `src/rhome_core/conformance.py` sits
inside an engine path but is the specification-to-test coverage registry —
nothing in `rhome_engine` or `rhome_core` imports it; only `tests/conftest.py`
and the layer audit do. Registering a conformance clause is not a model change,
and treating it as one would make every stage that adds coverage forfeit its
freeze date. So it is excluded — and because an exclusion is a hole the moment
someone imports what it excludes, a test scans the engine's own source for an
import of anything on the excluded list.

## The record

```bash
python3 tools/freeze_version.py show     # the tree as it stands, records nothing
python3 tools/freeze_version.py freeze v0 --defect LIM-38
python3 tools/freeze_version.py verify   # has anything moved since?
python3 tools/freeze_version.py list
```

`data/model_versions.json` is append-only. `record()` refuses a repeated label
and refuses an unchanged model under a new label, because a freeze happens
once and a second freeze of the same thing is a way of quietly resetting a
date.

## What this does not do

It does not score anything. No prospective session has been read, and none will
be until a version is frozen and a stage sets out to evaluate it — this stage
only makes that possible. It also does not verify that a *logged* session
post-dates a freeze in any pipeline yet; `ModelVersion.covers()` exists and is
tested, but wiring it into an evaluation is the job of the stage that first
scores prospective data.

## Limitations

Recorded in `LIMITATIONS.md` as [LIM-39].

A source digest over whole files means a comment edit inside `rhome_engine`
changes the version. That is the safe direction to be wrong in — a spurious
"different version" costs a re-freeze, a spurious "same version" costs a false
claim about unseen data — but it does mean freeze dates will churn faster than
model behaviour actually changes, and a stage that only touches documentation
inside those paths will need a re-freeze it does not deserve.
